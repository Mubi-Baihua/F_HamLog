## 更新界面两个 Qt 坑：叉号关不掉 / 进度窗不能最小化
- 用户反馈：①「本地已有安装包」那个 QMessageBox **点叉没反应**；②下载进度窗**没有最小化按钮**。
- **根因 1（很重要，通用）**：`QMessageBox` 在**没有任何 RejectRole 按钮时，标题栏叉号和 Esc 都失效**。
  实测三组：只有 Accept → 能关；Accept + Action（我们原来的写法）→ `close()` 完全无效，只能靠
  `done()` 兜底；Accept + Action + Reject → 能关。所以「不想放取消按钮、让用户点叉」这条路在 Qt 上根本不通。
- 修法：`_ask_cached` 改**自己排按钮**（QDialog + QVBoxLayout + QHBoxLayout + 3 个 QPushButton）。
  顺带按 role 重排的坑也没了 —— QMessageBox 在 Windows 上 RejectRole 永远紧跟 AcceptRole，
  三按钮必是 [立即安装][稍后][重新下载]（试过 Yes/No/Destructive role 组合，结论一样）。
  现在顺序是 [立即安装][重新下载][稍后]，叉号 / Esc / 「稍后」三条退路都返回 `''`。
  对话框 `setMinimumWidth(460)` + `setMaximumWidth(600)`：长路径自动换行又不会把窗口撑爆。
- **根因 2**：QProgressDialog 默认 windowFlags 里没有 `WindowMinimizeButtonHint`。
  但**只补最小化 hint 会多出一个灰掉的禁用「最大化」方块**（Windows 看到「有最小化、没最大化」就这么画）；
  一起给 `WindowMaximizeButtonHint` 后三个按钮才都是正常状态（已验证最小化/还原都正常）。
- 顺带把进度窗从 `Qt.WindowModal` 改成 **`Qt.NonModal` + parent=None**：
  模态时最小化自己之后父窗口仍被阻塞，点了没反应，比不能最小化更像卡死；非模态后可以最小化去干别的，
  也能继续用主界面。parent=None 是为了「下载期间关掉设置窗口不中断下载」（有父对象会被带走）。
  代价是 `_ok`/`_fail` 里拿到的 window 可能已经销毁 → 新增 `_alive()` 探活（碰 C++ 对象捕获 RuntimeError）。
- 新增模块级 `_update_dialog`：重复触发检查更新时把已有进度窗 `showNormal()+raise_()`，不再开第二个；
  关窗后 `_shut()` 里清引用。
- 测试：新增 `tests/__update_dialog_smoke.py`（24 项）——叉号/Esc/稍后/立即安装/重新下载五条出口、
  按钮顺序与默认按钮随 verified 变化、非模态、最小化 hint、最小化+还原、重复触发复用窗口、关窗停线程。
  真实 Windows 平台抓整窗截图（屏幕截图按 frameGeometry 裁剪，`grab()` 抓不到标题栏）确认外观。

## 改回：判「同一个包」只看 exe 名称，不再比版本号（推翻上一节的 J4–J6）
- 上一节那道「文件名版本 vs 目标版本」核对是**净负担**：命名规则并不统一，`F HamLog 2.9 setup.exe`
  配版本 `2.9.0` 时，`_same_or_older` 双向比出来的结果是「不等」（`2.9` 补齐成 `2.9.0` 只在一个方向成立），
  已经下好的包被判成「不是这个包」→ 每次点下载都白重下几十 MB。
- 新增 `check_update.installer_name(path_or_url)`：只取文件名，小写，把空格/点/下划线/连字符都当分隔符
  （URL 里的 `%20` 也先 unquote）。`find_installer()` 的候选按它比对；**`version` 参数只为兼容保留、不参与判断**；
  元数据里也只比 url + size（大小不同 = 被截断或被换过）。真正要防的「装回旧版」由下载地址本身兜住 ——
  我们要装的本来就是这个地址指着的文件。`_version_matches_name()` 整个删掉。
- 测试 J4–J6 重写：版本参数不影响判断、名字归一化（大小写/分隔符/URL 编码）、名字不同就是另一个包。

## 发布 2.8.0 卡在创建 Release（403 Resource not accessible by integration）
- 现象：run #40160945050 全程只有最后一步「发布到 Releases」失败，`gh release create` 返回
  `HTTP 403: Resource not accessible by integration`；同一次 run 里「提交产物到运行分支」**推送成功**
  （develop 上出现 `5df93b2 打包 2.8.0 [skip ci]`）→ 证明 token 确有 `contents: write`，
  **不是** `permissions:` 没写（工作流里本来就有 `contents: write`）。
- 真因（GitHub REST docs / Create a release 的 Note）：`target_commitish` 相对**默认分支**新增或修改了
  `.github/workflows/` 下任何文件时，创建 Release/tag 的 token 必须具备 **workflows 写权限**；
  否则 404，部分调用路径返回 403 Resource not accessible by integration。**GITHUB_TOKEN 永远拿不到
  workflows 权限**（YAML 里写 `workflow: write` 也没用）。
  本次 run 在 `develop` 上触发（head_sha `cc10a73`），该提交相对 `main` 改了 `main.yml`(+24) 与
  `preview.yml`(+63) → 必然 403。2.7.0 成功是因为它在 `main` 上发布。
- 结论/规则：**发布只在默认分支 main 上点 Run workflow**；要换用 PAT 才有解。产物回写分支只需
  contents，跟这条限制无关，所以「前面全成功、只有最后一步 403」是常态，极具误导性。
- 已加防护：`main.yml` 新增「预检 Release 权限」步骤（放在打包**之前**，几秒内失败），用
  `gh api contents/.github/workflows` 按「文件名=blob sha」比对当前提交与默认分支，不一致就抛出
  带解决办法的中文报错；文件头部也加了「必须在 main 上发布」的提示。
- 另记：`--target` 传的是 `GITHUB_SHA`；不要给这里加 `workflow: write` 权限，纯属无效。

## 预检步骤的显示 bug（Compare-Object 方向写反）+ main 快进
- 现象：在 develop(bb9ebda) 发布时，预检报「[仅当前提交有] main.yml=e5097c6e / [仅 main 有]
  main.yml=0a0ad39」，**方向完全颠倒**。本地实测 main(0379f9b) 的 blob 是 e5097c6e（旧、
  有 15 处兼容版、**无**预检步骤），develop(bb9ebda) 是 0a0ad39（新、有预检）。
- 真因：PowerShell `Compare-Object` 的 **SideIndicator 语义**：`'<='` = 只在
  ReferenceObject（第 1 个参数）里；`'=>'` = 只在 DifferenceObject（第 2 个参数）里。
  原代码写成「'=>' → 仅当前提交有」，正好反了 → 让「main 太旧」看起来像「本地比 main 新」。
- 已修（f4b0ed8）：显式 `-ReferenceObject $cur -DifferenceObject $def` + `'<=' → 仅当前提交有`，
  并把这条语义写进注释（极易复发）。
- 顺带确认：**main 无任何独有提交**，落后 develop 18 个提交 → 纯快进，不需要合并提交。
  推送 f4b0ed8 到 refs/heads/main 完成（0379f9b..f4b0ed8），远端 main = develop = f4b0ed8。
- 规则：发布前先 `git rev-list --count main..develop` 与 `develop..main` 判断快进还是合并，
  再决定要不要造 merge commit；`merge-tree --write-tree` 可零工作区开销地预演合并。
