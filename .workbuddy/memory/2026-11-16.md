## 修复「批量记录自动保存没用」+ 复选框文案

### 现象与真因
- 用户报「无法实现自动保存」：勾「自动保存到日志文件」→ 选「添加到默认通联日志」→ 完成，
  记录却没有真的留在 `main.fhla` 里（现场：`file/main.fhla` 0 条，`file/batch_backup.fhl`
  还留着未保存记录）。
- 真因**不是**保存逻辑本身，而是**同一个项目文件被两个窗口打开**（主页「通联日志」点两次
  就会这样）：A 写盘后，B 的内存还是打开时的空内容，B 下一次静默保存（`save(message=False)`
  的「首次必执行」分支）把整份文件覆盖回旧内容 → 刚写进去的记录消失。
- 用 `tests/__tmp_diag_*.py` 复现：两个窗口开同一 `main.fhla`，A 追加 → B `save()` → 文件被清空。

### 改法（project.py）
- 模块级：`_file_stamp(path)` → `(st_mtime_ns, st_size)`；`_same_file(a, b)`；
  `_doc_windows`（每窗口登记「取当前路径 / 重载」）+ `notify_file_changed(path, skip=window)`
  （`_notify_busy` 防互相重载循环）。
- `main()` 内：`_disk = {'path': save_path, 'stamp': _file_stamp(save_path)}`；
  `_reload_from_disk(path)`；窗口登记进 `_doc_windows`。
- `save()`：**外部改动检查放在「内容没变就跳过」之前**（顺序错了测不出来）——
  指纹变了且本窗口没改过（`_cur == _fhla['open_snap']`、`_fhla['dirty']` 为 False）→ 重载并
  直接 `return True`（不写盘）；本窗口也改过 → 以本窗口为准，写完对齐指纹。
- `_write_project_file()`：写完更新 `_disk`，并 `notify_file_changed(path, skip=window)`。
- `_reload_from_disk()` 的护栏：**有未保存改动**（`_content_snap() != _bk_state['last']`）
  或**正开着单元格编辑器**（`table.state() == QAbstractItemView.EditingState`）→ 不重载，
  避免吞掉用户正在编辑的内容。
- `batch_project.apply_save_target()` 写完（非 remote）调 `project.notify_file_changed(path)`，
  这样「主页打开的 main.fhla」窗口会立刻看到批量记录写进来的行。

### 复选框文案
- 选「添加到默认通联日志」→ 复选框回到「自动保存到日志文件」（不挂 `（main.fhla）`）；
  只有选具体文件才显示 `（xxx.fhla）`。
- `project._batch_log_name()`：当前项目就是默认通联日志时返回空串（同样不挂文件名）。

## 批量记录「自动保存到日志文件」= 边改边写（实时同步，定稿）

需求：勾了自动保存后，批量记录里**每改一格 / 每新建一列**都要同步到那个日志文件，
项目窗口的表格要跟着显示（不是等点「完成」）。

### 接口
- `batch_project.main(..., sync_io=None, auto_target_path=None)`：
  `sync_io = {'read': () -> (records, token), 'write': (records, token)}`；
  项目窗口启动时由 `project._live_sync_io()` 提供（读 = 本窗口记录列表，写 = 原地替换
  `file[:]` → 落盘/`send_save` → 增量刷新表格 → `_bk_clear/_bk_snapshot`），
  加密密钥 / `.fhla` 属性块 / 多人日志都走本窗口既有实现，不分叉。
  主页启动时用 `batch_project.path_sync_io(path, fresh=...)`（按文件指纹缓存解析结果）。
- `auto_target_path`：启动它的日志路径，只用于「点完成时又选了同一个日志」时去重。

### 同步算法（`_live_sync`）
- 只写**填完整**的列（必填 + 日期/时间格式）；没填完的列先跳过（日志里保留上次那条），
  全空的列视为删除。日期/时间留空补当前时间，同一列只补第一次（`live['times']`）。
- 每列记 `pos`（写进日志后的下标）+ `wrote`（写进去的内容）：下次同步**就地改这一条**，
  位置对不上才按内容找回、再不行才追加——宁可多一条也不覆盖别人的记录。
- 删除列：`_live_shift_cols(at, -1, removed=(idx, rec))` 把这条塞进 `live['gone']`，
  下次同步删掉；增列 `+1` 只挪列号键。
- 触发：`cellChanged`（c≥1）、`_insert_col`/`_remove_col`、`_CellCmd._apply`（撤销/重做）
  → `_live_touch()` 置 pending + 400 ms 单次防抖定时器 → `_live_sync()`。
  内容与 `live['last']` 相同则不写盘。
- 「完成」不再整份追加：先 `_live_flush()`，成功就关窗。目标做不了实时同步时
  （多人日志 / 加密日志没密钥 / 项目还没保存路径）退回老路径：`on_saved` 或 `auto_pick`
  一次性写。**中途取消勾选又点完成**：`live['detached']` 记下已同步的那几条，
  只有仍写回同一个日志才剔掉（否则会重复追加）。
- 未保存判定：实时同步下 `_bk_is_dirty()` = 还有「填了但没填完」的列（`_pending_input()`）；
  已同步的记录不算未保存，关窗不追问；没填完的列会拦下来并留 `batch_backup.fhl`。

### 性能
- 1 万条日志里同步一条：**整表重建 1.10 s → 增量 0.49 s（含 400 ms 防抖，实际写+画约 0.09 s）**。
  做法：`project._table_sync_from_file(old)` — 只改几条走 `table_refresh_row`（date/time 变过
  则重建，顺序会变）、纯末尾追加走 `_append_table_rows`（`_fill_rows(..., start=n)`）、
  其它（删除 / 行数变少）才 `table_update(persist=False)`。

  U1–U7（取消勾选后完成不重复、换日志照样写、再勾回来仍就地更新）、V1–V5（未保存判定）。

## 更新下载：定长分段 → 动态分块（解决「前面快、后面慢」）

- 触发：用户要求「下载更新时动态划分多线程的分块，不要前面快后面慢」。
- 根因（三条叠加）：
  1. 旧的 `_download_parts` 是**定长 N 段、段数 = 线程数**：快的线程下完就闲着，收尾只剩一两条连接在跑 →
     进度条最后 10% 明显变慢。
  2. CDN / 镜像对每条连接都是「先给一阵高速再单连接限速」，N 条连接同时建立 → 差不多同时被掐，
     聚合速度中途下一台阶。
  3. 全部下完还要「合并 N 个分段」（100% 之后仍要读一遍整包）→ 看着像卡死。
- 改法（`src/f_hamlog/check_update.py`）：
  - 新增 `chunk_bytes(total, workers)` / `chunk_spans(total, workers)`：块数 ≈ `workers × CHUNK_SPLIT(3)`，
    单块夹在 `[PART_MIN_BYTES(512KB), CHUNK_MAX_BYTES(8MB)]`，并二次均分避免末尾碎块。
  - `_download_parts` → `_download_parallel`：共享队列（`state['next']` + 锁）抢块 + `min(workers, 块数)` 线程；
    **按偏移直写 `dest.part`**（`open(..., 'w+b', buffering=0)` + `truncate(total)` 预分配 + `io_lock` 保护
    `seek/write`），写完直接 `os.replace` → 无合并阶段。
  - 每块一条新连接 → 天然复用「刚建连那阵高速」；`_check_range()` 校验 206 + Content-Range 起点，防止
    代理不认 Range 时字节写到错偏移（静默损坏）。
  - 重试改为**按进展计**：`stalls`（连续零进展）到 `PART_TRIES` 或总次数到 `PART_TRIES×8` 才判死，断线从
    `pos` 续传（不再 `meter.add(-got)` 回退，进度天然单调）。
  - 某块彻底失败 → `stopped.set()` 让其余线程收手 → 抛错 → `_download_once` 仍按老路退回单线程。
  - 删掉 `import shutil`（合并用的）。
- 测试：`tests/__update_download_smoke.py` 重写（A 组断言块数 = 线程数×3、单请求 ≤ 单块、块均分、无 `.part`
  残留；新增 D 组「先给 384 KB 高速再限速 256 KB/s」的服务器，旧实现 4.47 s vs 动态分块 1.19 s ≈ 3.7×）。
  临时验证过断流续传（每连接只给 100 KB，92 个请求拼完）、单块 500 退回单线程、服务器不认 Range 退回单线程。
- 顺带修 `tests/__update_flow_smoke.py` 的过期断言 F0（原断言「检查期间按钮变灰」——早已定稿为只改文字
  不禁用，改为断言 `isEnabled()` + 文字「检查中…」）。
- 回归：download 14/14、cache 32/32、source 16/16、dialog 26/26、flow 30/30 全过。

## `main.yml` 发布版本号改为从 `__init__.py` 读取

- 需求：让 `main.yml` 从 `__init__.py` 取版本号（版本单一来源，不再手填）。
- 改法（`.github/workflows/main.yml`）：
  - 删掉 `workflow_dispatch.inputs.version`（原 `required: true`）与 `IN_VERSION` 环境变量；
    头部注释改成「版本号取自 `src/f_hamlog/__init__.py`，要发新版本先改它再 Run workflow」。
  - **步骤顺序调整**：「检出代码」从第 3 步挪到第 0 步（原来在「预检 Release 权限」之后，
    而解析版本号又排在预检之前 —— 不先检出就没有文件可读）；编号保持 0 / 0a / 0b，下游 1–5 不动。
  - 解析逻辑：`[System.IO.File]::ReadAllText($init, UTF8)` + 正则
    `__version__\s*=\s*["']([^"']*)["']` → Trim；再按 `^\d+\.\d+(\.\d+)*$` 校验
    （预览串 `Preview UTC-…` 直接 `throw`，防止误发正式版）；其余 `DISPLAY`/`SETUP_BASE`/
    `ASSET_SETUP`/`RELEASE_TITLE`/`COMMIT_SETUP` 推导不变。
  - `CONTRIBUTING.md` 中英文两处 `main.yml` 说明补一句「版本号取自 `__init__.py`，无需手填」。
- 验证：pyyaml 解析通过（inputs 只剩 6 项，steps 前 5 个 = 检出 / 解析版本 / 预检 / 设置 Python / 缓存 pip）；
  本机 PowerShell 实跑解析 → `version=2.9.1`、`display=2.9.1`、`setup=F HamLog 2.9.1 setup.exe`，
  且 `Preview UTC-20261116-0330 2.9.1` 被格式校验拦下。
- 影响：Release tag = `__init__.py` 的版本号；同一版本重复跑仍走「Release 已存在 → `--clobber` 覆盖附件」。
