## 修复：打开主界面（main.py 启动器）时布局上下跳一下

**症状**：启动程序后主窗口出现，内容会竖向跳一下（约 6~14px）。

**取证方式**（真实平台，非离屏）：把 `QMainWindow.show()` 包一层，在 App 事件过滤器里
记录 Move(13)/Resize(14)/LayoutRequest(76) 及每次的 geometry，时间戳打印。结果：
`show()` 内部第一遍排布网格在 y=174 高 130，`show()` 返回后又排一遍变成 y=180 高 124，
主按钮同一时刻从 h=40 变 h=46。→ 两遍排布结果不同，用户先看到一帧再看到另一帧。

**两个根因**（都在 `src/f_hamlog/main.py`）：

1. 竖向过度约束：窗口固定 575×375，而这一列内容的自然高度约 390px（边距 34 + 标题 31 +
   副标题 17 + `addSpacing(50)` + 主按钮 46 + 网格 132 + 分隔线 3 + 设置 40 + 6×6 间距）。
   多出的高度没处去，只能从两列 `QGridLayout` 里挤（行距被压成 3~4px 且不均匀），
   而这次挤压发生在 `show()` 之后（QSS 抛光会让布局重算）。
2. `_style_btn(primary=True)` 里的 `btn.setMinimumHeight(BTN_H)`：在调用处已
   `setFixedSize(220, 46)` 之后又设最小高 40，把「固定 46」变成「40~46 可伸缩」，
   两遍排布各取一个值 → 主按钮跳 6px。

**改法**：
- `addSpacing(50)` → `addItem(QSpacerItem(20, 50, QSizePolicy.Minimum, QSizePolicy.Expanding))`
  可压缩留白吸收溢出（实测留白变 42px，其余位置一次到位）。
- 删掉末尾 `addStretch(1)`（两个可伸缩项时余量按 stretch 分给末尾，留白仍 50 → 等于没改）。
- 删掉 `setMinimumHeight(BTN_H)`（高度全部由调用处的 `setFixedSize` 定死）。

**验证**：
- `tests/__main_layout_settle_smoke.py`：show() 返回瞬间快照全部子控件 geometry，
  300ms 后再比，有任何变化即 FAIL。必须 `QT_QPA_PLATFORM=windows` 跑，离屏字体小、
  内容不超高，复现不出来。
- 负向对照：临时换回 HEAD 的 main.py → 冒烟 FAIL 并逐条列出 5 处变化（主按钮 40→46、
  卫星过境 46→44、新建/打开 91→87、网格 174/130→180/124）；改回后 PASS。
- `tests/__main_grab_probe.py` 抓首帧图确认观感：网格行距均匀 6px、底边距 16 正常。

**注意**：`setFixedSize` 之后再 `setMinimumHeight/setMaximumWidth` 会把固定尺寸解成区间，
布局两遍排布可能取不同值 —— 这是本次跳动的第二半原因，别再加回来。

## 结论：`.fhl` 直接改名成 `.fhla` 能被正常识别（实测）

用户问「main.fhl 改为 main.fhla 可以正常识别吗」。实测（`tests/__rename_fhla_probe.py`，
明文与 AES-GCM 加密两种都试过）——**可以**：

- `project.build_project()` 有专门的 list 分支（注释原话「把 .fhl 直接改名成 .fhla」），
  `parse_fhla_text` 解析出 list 后自动包成 `{'xml': {}, 'project': [...]}`。
- `is_fhla_path()` 大小写不敏感；`default_quick_project_path()` 优先 `file/main.fhla`，
  改名后「通联日志」直接打开新文件，也不会再问迁移（`offer_migration` 只对非 .fhla 生效）。
- 加密 `.fhl` 改名同理：读时不按扩展名、按字节判加密 → 解密后同样得到 list → 正常包。
  不给 key 时返回 `(None, None)`，与 .fhl 行为一致（不会挂死）。
- 唯一可见差异：改名的文件**首次保存前**属性块是空的（创建者/创建时间显示为空），
  一旦编辑保存就变成标准 `.fhla`（`mark_edited` 会顺带补 creator）。走程序内「迁移」
  则当场就带属性块 —— 两者记录的日志内容完全一致。
- 别「复制」要「改名」：两个文件并存时 `.fhla` 胜出，留下的旧 `.fhl` 会变成孤儿
  （万一 .fhla 被删就退回旧内容）。

## 结论：默认日志改成 .fhla 后，多人日志照常可用（格式解耦）

用户问「改用新格式后多人日志可以用吗」。追代码确认 **可以，且与格式完全解耦**：

- 多人日志内部只玩「内存记录列表 + 房间文件 `多人日志_YYYYMMDD_HHMMSS.fhl`（纯 list）」，
  从不依赖默认日志是 `.fhl` 还是 `.fhla`（`project.py:4192-4193` 房间文件恒 `.fhl`）。
- 开放多人日志以当前内存 `file`（来自 main.fhla 的记录）作种子
  （`seed_list=copy.deepcopy(file)`，project.py:4204），与默认日志扩展名无关。
- 多人日志期间 `save()` 走 `rc.send_save(file)`（project.py:2242），**不动本机文件**；
  退出 `_detach_remote` 只断连、重算未保存基线（project.py:4008-4025），不回写 main.fhla。
- 唯一跟 `is_fhla_path(save_path)` 挂钩的是「项目属性 / 自定义字段」两类窗口
  （project.py:2550 / 2584）—— 默认日志变 `.fhla` 后**反而能用**（之前 `.fhl` 会提示不支持）。
- 既有注意（与格式无关，非回归）：多人日志期间的改动存在房间文件与内存，退出后
  main.fhla 不会自动回写，需手动另存/导出。

## 过境视图改成独立顶层窗口（最小化来源窗口不再连带）

用户口径：「最小化过境预测时，视图窗口不要最小化」。

- 根因：`open_sky()` 里把来源窗口当 Qt 父对象传给 `SkyWindow(parent, ...)`，于是视图成了
  Windows 的「被拥有窗口（owned window）」，主人一最小化它就跟着最小化；同时也失去自己的任务栏按钮。
- 改法（与既有 `satellite_map_window.open_map()` 完全一致）：`SkyWindow(None, ...)` 建独立窗口，
  来源窗口只记在 `win._source`（仅供定位与调试），新增 `_place_near(win, ref)` 把视图摆在来源窗口
  中央并夹在工作区内。重复点同一行时若那个视图被最小化过，先 `showNormal()` 再聚焦。
- 验证：`tests/__sky_view_integration.py` **34/34**，新增两条
  （「视图窗口没有父窗口（独立顶层）」`sky1.parent() is None and sky1._source is w1`、
  「最小化来源窗口后视图仍可见」`showMinimized()` 后 `isVisible()` 且 `not isMinimized()`）；
  `tests/__sky_view_smoke.py` **51/51**，两种平台（offscreen / windows）都跑过。
- 实测输出：`sky parent None | parent minimized True | sky minimized False | sky visible True`。
